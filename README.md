# STP1: Boundary-aware calibrated gating for sensitive agent actions

CS 48013/58013 Human-Centered AI, Short-Term Project 1 (Project 12: user-defined boundaries for AI agents and sensitive actions).

The code decides whether a tool call proposed by an AI agent should be **executed**, **confirmed with the user**, or **blocked**. It compares two baselines, two human-centred designs and their ablations on a seeded, fully synthetic scenario suite.

| Policy | What it does |
|---|---|
| `B0_broad` | Executes every proposal (one-time broad permission). |
| `B1_always_ask` | Asks before every proposal. |
| `A_rules` | **Design A.** Applies the user's stated allow/ask/deny rules directly. Unruled pairs fall back to a static tier: irreversible or external actions → ask. |
| `B_full` | **Design B.** Gradient-boosted P(approve) from action features plus the user's boundaries, with isotonic calibration. Deny rules are hard constraints; an allow rule is never silently blocked (escalated to ask). Cost-tuned three-way rule: execute if p ≥ τ_hi, block if p ≤ τ_lo, ask in between. |
| `A_no_ask_tier` | Ablation of A: removes only the static risk tier (unruled pairs execute). Explicit allow/ask/deny rules are unchanged. |
| `B_no_boundaries` | Ablation of B: removes only the boundary *features* from the model. Deny rules and the allow→ask floor are still enforced. |
| `B_no_ask_band` | Ablation of B: forces τ_lo = τ_hi (no model-triggered asks). Allow-ruled actions the model would block are still escalated to ask, so some asks remain. |
| `B_soft_deny` | Ablation of B: deny rules are no longer hard constraints. |

## Environment

- Python 3.11 (the reported results were produced with Python 3.11.13 on Windows 11; the same pinned packages also gave identical numbers for the unchanged policies on macOS 14 with Python 3.11.7)
- `pip install -r requirements.txt` (numpy 1.24.3, pandas 2.0.2, scipy 1.11.3, scikit-learn 1.3.2, matplotlib 3.8.1). These pins have no wheels for Python ≥ 3.12. With [uv](https://docs.astral.sh/uv/): `uv venv --python 3.11 .venv` then `uv pip install --python .venv -r requirements.txt`.
- No GPU, LLM, API key or external data needed.

## Run

```bash
python run_experiments.py --seeds 10 --out results   # ~4.5 min on a Windows 11 laptop
python make_figures.py --res results --fig report/figures --tab report/tables
```

`run_experiments.py` writes to `results/`:

- `per_seed.csv`: every policy × seed × habituation level
- `summary.csv`: mean ± 95% t-CI across seeds
- `subgroups.csv`: by user archetype, reversibility, rule presence and mistake type. Each subgroup is a slice of the same resolved test run as the main table (same seed and per-user fatigue).
- `calibration.csv`: AUROC, Brier and ECE of the risk model, raw vs. isotonic
- `coverage_per_seed.csv` and `coverage.csv`: rule-coverage sweep (seeds 0–4), per seed and summarised
- `data_stats.json`: test-set statistics and tuned thresholds per seed
- `cases_seed0.json`: representative successes and failures, including over-blocking cases

`make_figures.py` writes the figures and LaTeX tables, and also `results/paired_ablation.csv`: paired (same-seed) differences, ablation − full design.

## Data

Fully synthetic. The data is generated by `boundaries/sim.py`, with no personal data and no licence restrictions.

- 300 users per seed from 3 archetypes: conservative 30%, balanced 45%, delegator 25%.
- Each user receives 60 proposals.
- 8 tools, 5 data categories, 5 recipient classes, 3 scope levels.
- Ground truth: the user approves iff a latent score > 0. The score combines tool risk, data sensitivity, recipient, scope, a per-user × (tool, category) offset (σ = 0.6) and action noise (σ = 0.5).
- **Boundaries:** each user writes rules for 60% of the 40 (tool, category) pairs. Rules come from the user's typical score (allow > 1, deny < −1, else ask) and are flipped with probability 0.05.
- **Injected agent mistakes (15%):** off-task, wrong recipient, overbroad scope.
- **Split by user:** 60/20/20 train/val/test, i.e. 180/60/60 users per seed. Test users are unseen.
- **Seeds:** 0–9 for the main runs, 0–4 for the coverage sweep. The seed controls data generation, the split (`seed + 999`), model `random_state` and simulated confirmation responses. Threshold tuning uses a fixed RNG seed of 12345.

## Model and settings

- `HistGradientBoostingClassifier(max_iter=300, learning_rate=0.05, max_leaf_nodes=31, early_stopping=True)`: early stopping uses a 10% internal validation split and stops after 10 iterations without improvement (this is also scikit-learn's default behaviour above 10,000 training rows).
- `CalibratedClassifierCV(method="isotonic", cv="prefit")`, fitted on validation users.
- Thresholds: grid 0.02…0.98 (step 0.02), chosen on validation users to minimise expected cost at k = 0.15. The same thresholds are reused when reporting k ∈ {0, 0.30}. Only Design B and its ablations have tuned parameters; B0, B1 and A have none.
- Simulated confirmation: the user answers correctly with probability `max(0.98 − k · ask_rate, 0.5)`, where ask_rate is the share of that user's proposals that asked. The default is k = 0.15, and the scripts also report k ∈ {0, 0.30}.

## Metrics

| Metric | Definition | Why |
|---|---|---|
| UER | P(executed \| user would not approve), including wrongly confirmed actions | Primary safety outcome |
| FBR | P(not executed \| user would approve) | Over-restriction |
| Ask rate | Share of proposals that trigger a confirmation | Interruption burden |
| Autonomy | P(executed without asking \| approve) | Delegation benefit |
| Mistake exec. | P(executed \| injected agent mistake), including mistakes the user wrongly confirmed | Robustness to agent errors |
| Mistake catch | Share of injected mistakes that were asked about or blocked (not silently executed) | How often the gate gives the user a chance to stop a mistake |
| Block rate | Share of all proposals blocked without asking | Silent over-restriction |
| Cost | Mean per proposal: 10 × unintended + 2 × false block + 1 × ask | One-number summary. Depends on the weights. |
| AUROC | Probability that a random approved action gets a higher P(approve) than a random unapproved one | Discrimination of the risk model |
| Brier | Mean squared error of P(approve) | Overall probability accuracy |
| ECE (10 bins) | Weighted mean gap between predicted P(approve) and observed approval rate per bin | Calibration of the risk model |

Rates whose denominator is empty in a subgroup (e.g. no unwanted actions) are reported as missing, not as 0. Uncertainty is reported as mean ± 95% t-interval over seeds. Ablations use paired (same-seed) differences.

## Known limitations

- Fully scripted and synthetic. No real LLM agent is involved, and the results should not be generalised to LLM agents. Prompt injection is only approximated by the off-task mistake type.
- Synthetic ground truth from the same feature family the model sees. This favours learned models, so the results are not evidence of a benefit for real users.
- Simulation parameters (archetype mix, preference weights, mistake penalties) were set after inspecting the resulting base approval rate.
- Some differences are partly built into the setup: only Design B is tuned on the evaluation cost and the simulated user; B1's ask cost alone gives it a cost of at least 1, and its UER follows from the fatigue assumption; Design A's rules are written for the typical recipient and single-item scope, so A cannot see the recipient and scope changes that define two of the three mistake types.
- The `relevance` feature is a noisy signal that separates off-task mistakes (Beta(2,5) vs. Beta(5,2)). Only Design B sees it, and a real agent may not have such a signal.
- Users are assumed to state rules consistent with their preferences (up to a 5% flip rate).
- The fatigue model is a single linear term in the per-user ask share.
- No online learning from confirmation answers.
- The cost weights are a value judgement.
- Not a security boundary. Do not use it with real accounts or actions.
